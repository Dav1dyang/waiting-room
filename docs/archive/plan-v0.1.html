Concept review and build plan

claude-omegle

While your Claude works, you are on a call with a stranger whose Claude is also working. When either Claude finishes, the call ends. Every wait, a different stranger.

Working title. See Q-01. Written 2026-09-05 Claude Code 2.1.261 verified 4 research memos, linked in section 11
Summary
  • The idea holds up, and nobody has built it. About fifteen Claude Code plugins already fill agent wait time with games, pets, or music. All of them are solo. Two Zoom patents describe the same mechanic for call-centre queues. The specific fusion, a stranger matched by "Claude is working" and released by "Claude is done", is unoccupied.
  • Its best idea is the blameless exit. Omegle's "Next" was a rejection. A hang-up that a machine imposes leaves nobody rejected. But it needs a floor: a call cut after forty seconds feels worse than being skipped. So short turns never trigger a call, and the threshold is measured from your own usage, not guessed.
  • It can be built small and run for $0. A plugin with six hooks and one command, one static web page, and one Cloudflare Worker with one Durable Object, the same pattern as your Mist Maker relay. Media goes browser to browser. Cost stays at zero up to roughly 4,400 calls a day.
  • The hard parts are not technical. Two Claudes rarely overlap in a small group, so "waiting alone" must be the good default state. And video with strangers always needs a safety story, so the MVP is invite-only, audio-first with a mutual "show video" click, with skip limits and a kill switch from day one.
  • Start with one hour of instrumentation (Phase 0) before writing any product code: log your own turn start and stop times for a week. That one dataset sets the two numbers the whole design depends on.

01 · What you asked, answered plainly

How does a Claude Code plugin work?
A plugin is a folder with a small manifest. It can add slash commands, skills, agents, MCP servers, and hooks. A hook is a shell command that Claude Code runs at a lifecycle moment (prompt submitted, tool used, turn finished, session ended) and feeds a JSON description of that moment on stdin. This project needs only hooks and one command. Hooks run silently and can be marked async so Claude never waits on them. Two facts that shape the design: plugin hooks are installed without an approval prompt, so the plugin ships disabled and you turn it on with a command; and the Stop hook does not fire when you press Escape, so the web side needs its own timeout.
How does one know how long the response will take?
One doesn't, and the plugin never tries. Claude Code has no duration estimate and no timestamp in any hook payload. What it does give is an exact start (the prompt is submitted) and an exact end (the turn stops). So the design observes instead of predicting: a call only opens after Claude has already been working for a threshold (placeholder 30 s), because turns that pass that point tend to be the long, agentic ones. The threshold comes from a week of your own logged turns (Phase 0). Reported waits in the community range from ten seconds to twelve minutes, so the distribution is wide and two-humped.
How do we get permission to open a call to a stranger?
Three layers, none of them silent. (1) Installing the plugin and running /claude-omegle:omegle on is explicit opt-in per machine. (2) The web page shows a rules screen once, and an Available / Away switch always; closing the tab is the off switch. (3) The browser's own camera and microphone prompt, per site. The first click on the rules screen also satisfies the browser's "user gesture" rule for playing the stranger's audio. Between calls, the camera light is off. Nothing about your prompts or code ever leaves the machine.
Can it be free, with a free server and backend?
Yes. Static page and signaling run on the Cloudflare Workers free plan with one Durable Object, which is exactly what your Mist Maker relay already does. Audio and video go directly between the two browsers. The only paid-looking piece is the relay some networks need (TURN), and Cloudflare gives 1,000 GB a month of it free. At a hundred five-minute calls a day the bill is $0, and the first cent arrives around 4,400 calls a day. One thing to confirm in your dashboard: whether a free account can create a TURN key without a card on file. If not, Metered's Open Relay gives 20 GB a month free.
What does the MVP look like?
A plugin (six hooks, one command, a pairing token), one web page (rules, waiting alone, in call, goodbye), and one Worker with one Lobby object (queue, pairing, signaling, timeouts, invite code, ban list, kill switch). Audio first, video by mutual click. Skip, Report, Away. A live count of who is online. Invite-only. Roughly 200 lines of Worker, 400 lines of page, 60 lines of plugin. Section 04 has the scope fence.
What systems thinking is needed?
Two things. A state machine for the tab, because the "Claude is working" signal is unreliable at the edges and every state needs a way home. And a liquidity model, because a matching product only works above a critical number of people online at the same moment. Section 07 works both out with numbers.

Prior art: the exact idea is unoccupied

Searches across GitHub, Hacker News, and the open web found no project that pairs two humans because both their agents are busy. What exists nearby:

  • Solo wait-fillers for Claude Code (while-you-wait, claudemon, waitingfor.ai, elevator-music, several arcades, desktop pets, even an ad network that pays you while Claude works). Same trigger, same hook plumbing, no person. This is the real competitive set and the honest claim: everyone fills the wait with content, nobody fills it with someone.
  • coderoulette: pair-program with a stranger and one shared agent for 30 minutes. Terminal only, demand-triggered. Its three-minute no-fault re-match is worth borrowing.
  • Zoom patents US 11,936,813 B2 and US 11,627,224 B1: collaborative virtual waiting rooms where strangers socialise until an agent picks up. Same mechanic, call-centre domain. Not legal advice, but worth knowing about before anything public.
  • Claude Code's own spinner verbs ("Pondering", "Marinating", 187 of them, user-customisable) are already a beloved loading-screen art practice. The wait is not blank territory; this is a new move inside an existing genre.
  • Reddit could not be searched by the research agents. Worth ten minutes of manual checking in r/ClaudeAI and r/cursor.

Six things the concept should absorb

  1. The blameless exit needs a floor. Below about a minute, a machine hang-up reads as an insult. Hence the threshold, the goodbye countdown, and a Phase 0 that measures how often a turn that passes 30 s goes on to pass 3 min.
  2. Waiting alone is the normal case. With twenty users, two Claudes overlapping is rare. The solo screen (your Claude's elapsed time, who is online, a live count that is never faked) must be worth keeping open on its own.
  3. Restrict the channel first. Audio with a mutual click for video is cheaper, safer, and closer to what people want during focused work. Try the Journey-style thin version (video on, mic off, a wave) as a Phase 3 experiment.
  4. The Portal shape of moderation. Mechanical, automatic, blameless: rate-limited skips, a hard cap on call length, one-click block, kill switch. Not a human queue you cannot staff.
  5. Design against obligation. Benjamin's boredom is where experience hatches; Bogost's social games "abuse us while we are away from them". Default off, easy to skip, no streaks, no scores, no history.
  6. Give the encounter one question. Portals opened with "What would make today a good day for you?" Yours can open with the one thing both people share: "What is your Claude doing?"

Honest weaknesses

  • Cold start is severe. This needs many people waiting at the same moment. A plugin with a hundred users will mostly produce empty rooms. Office hours and an honest live count are the cheapest fixes; see section 07.
  • Liability is out of proportion to a hobby project if it goes public with video. Invite-only is the primary legal mitigation, not a product preference. Omegle's fate turned on matcher design, which Section 230 did not cover.
  • The name. Omegle is a trademark with a dark legacy, and omegle.com is live again under a new owner, so "claude-omegle" now points at someone else's product. Candidates from the research: Meanwhile, Long Poll, Yield, Blocking, Interstice, Standby, with "civil inattention" as a tagline. My pick is Meanwhile: plain, warm, describes the thing exactly, and /meanwhile on reads well.

03 · How it works

Three pieces, and each one is small. The terminal only ever says two words to the outside world, "started" and "stopped" (plus a heartbeat). The lobby does the pairing. The two browser tabs talk to each other directly.

A call, in words

  1. Once: install the plugin, run /claude-omegle:omegle on. It creates a random pairing token on your machine and prints a URL. You open it, read the rules, click Available. The tab stays open, connected to the lobby.
  2. You give Claude a task. The UserPromptSubmit hook posts "started" with your token. The tab shows your Claude's elapsed time and starts a 30 s timer.
  3. If Claude finishes before the timer, nothing happens. You never see a call for a quick answer.
  4. If the timer passes, the tab joins the queue. The lobby shows you an honest count: "4 online, 1 waiting". If nobody else is waiting, you wait alone with your Claude's clock. This is the normal case.
  5. Someone else's Claude passes their threshold. The lobby pairs you, tells each tab who is "polite" (a WebRTC role), and hands out short-lived relay credentials. The two tabs exchange offer, answer, and ICE through the lobby, and audio connects. A chime and a flashing tab title get your attention. Both of you see both Claudes' elapsed time and a small pulse whenever either Claude uses a tool.
  6. Either of you can click "show video"; it turns on only when both have clicked. Either can Skip (rate-limited) or Report (ends the call, logs the pair).
  7. Your Claude finishes. The Stop hook posts "stopped". Your tab shows a five-second goodbye, hangs up, and returns to idle. The stranger sees "their Claude finished" and goes back to waiting.

The plugin side

A tested skeleton already exists in prototype/plugin/. It has five hooks (UserPromptSubmit, Stop, StopFailure, SessionEnd, Notification), passed claude plugin validate --strict, and delivered start, stop, and session-end events end to end on this machine. The MVP adds PostToolUse (D-18) and swaps Notification for PermissionRequest (D-21); those two are planned, not yet tested. The shape:

claude-omegle/
  .claude-plugin/plugin.json      name, version, description
  hooks/hooks.json                UserPromptSubmit, Stop, StopFailure, SessionEnd, Notification
                                  (tested)  + PermissionRequest, PostToolUse (planned)  all "async": true
  scripts/signal.sh               reads the hook JSON, POSTs {token, event, session hash}
                                  with a 2 s timeout, prints nothing, always exits 0
  scripts/toggle.sh               creates ~/.claude-omegle/{token,enabled}, prints the URL
  commands/omegle.md              /claude-omegle:omegle on|off

Why these hooks: UserPromptSubmit is "started". Stop is the normal end. StopFailure is the end on an API error. SessionEnd retires the session. PermissionRequest fires the instant Claude needs you (the Notification variant waits about six seconds). PostToolUse is the heartbeat that keeps the timeout honest and gives the stranger a pulse. The skeleton currently forwards the whole hook payload; the real script must project it down to token, event, and a hash of the session id, so prompts never leave the machine.

The lobby protocol

Six messages each way. That is the whole protocol.

DirectionMessageMeaning
hook → lobbyPOST /signal{token, event: started | stopped | tick, session}. Idempotent. A "started" also closes any stale call for that token.
tab → lobbyhelloAttach this socket to a pairing token; carries the invite code once.
tab → lobbyjoin / leaveEnter or leave the queue (after T, or on stop / skip / report).
tab → lobbyoffer / answer / iceWebRTC signaling, relayed verbatim to the partner.
tab → lobbyreveal"I am willing to show video." Video starts when both have sent it.
tab → lobbyreportEnds the call, records the pair of tokens for a manual block list.
lobby → tabstateYour own Claude's status as the hooks see it: working / stopped / tick, with the session set.
lobby → tabpresenceHonest counts: online, waiting. Never padded.
lobby → tabmatched{matchId, polite, iceServers}. Relay credentials are minted here, short-lived.
lobby → taboffer / answer / icePartner's signaling.
lobby → tabpeer_left{reason: their_claude_done | skip | report | dropped}. You go back to the queue.
lobby → taberrorRate limited, blocked, bad invite code, maintenance mode.

Two details carry the design. The lobby assigns the "polite" role at match time so the browsers can use the standard perfect-negotiation pattern without arguing. And "partner left" is detected from the WebSocket closing, which the lobby sees in seconds, not from the media connection, which can take half a minute to notice.

07 · Systems and design thinking

The liquidity model

A matching product has a critical mass. The question is not "how many users" but "how many people are online and waiting at the same instant". A rough model:

N  = people with the tab open right now  = total users × fraction of the day they are online
p  = fraction of online time spent past the threshold ("waiting")   ← Phase 0 measures this
chance someone else is waiting when you start ≈ 1 − e^(−(N−1)·p)
Total usersOnline fractionN online nowChance of a match (p = 0.2)Chance of a match (p = 0.4)
10 friends0.15 (a few hours a day, scattered)1.510%18%
40 people0.15663%86%
40 people0.5 (office hours: everyone told to show up in one window)2098%100%
100 people0.151594%100%

Two readings. First, ten friends scattered across a day will almost always wait alone, which is why the solo state comes first. Second, synchronising a small group (office hours) beats recruiting a large one, which is what Focusmate's fifteen-minute slots and the Portal's reduced hours both discovered. p is the lever the plugin itself controls: a lower threshold raises p but shortens calls toward the insult floor.

Loops and leverage

Reinforcing loop

Good encounter → keep the tab open tomorrow → more people online → more matches → more good encounters. This is the loop office hours are meant to kick-start.

Balancing loop, wanted

Bad encounter → report → block → fewer bad encounters. Must be one click and must have teeth (block by token, rotate the invite).

Balancing loop, unwanted

Feeling obliged to be on camera every run → fatigue → turn it off for good. Countered by default-off, Away, no streaks, no history.

Leverage points, in order

  • Honest live count (information)
  • Office hours (synchronisation)
  • Threshold T and timeout N (the two dials)
  • Invite gate (quality of the pool)
  • Lurker mode, later (raises p artificially, breaks symmetry)
